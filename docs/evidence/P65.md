# P65 – `install-runtime.py` deployte die Dashboard-WebUI nie mit

Date: 2026-09-29
Verification class: `LOCAL_VERIFIED` (Host-Rollout folgt)

## Auslöser

Direkt nach dem P64-Rollout (`install-runtime.py` lief erfolgreich, keine
Fehlermeldung): `/gazette`, `/api/gazette` und `/gazette/<datum>.html`
lieferten alle **404**. Grund: `install-runtime.py`s Ziel-Liste (`targets`
in `main()`) enthielt `web/webui.py` und die drei `web/observatory.*`
-Dateien **überhaupt nicht** – nur `runtime.py`, `decision.py`,
`event_history.py`, `memory/gateway.py`, zwei Skripte, Prompts/Configs und
das `village/`-Paket. Ein „erfolgreicher" Install hatte die Dashboard-Datei
schlicht nie angefasst; der laufende `ai-village-webui.service`-Prozess
lief unverändert mit dem alten Code weiter, ohne jede Fehlermeldung.

`village/release.py::RELEASE_FILES` (das vollständige Release-Manifest)
deklariert `webui.py`/`observatory.*` bereits korrekt seit langem – die
beiden Listen waren einfach nie synchronisiert; kein bisheriges
Arbeitspaket in dieser Session hatte je Grund, `webui.py` oder
`observatory.*` zu ändern, wodurch diese Lücke bis jetzt unentdeckt blieb.

## Sofortmaßnahme (Blocker für die P64-Verifikation)

Manuell nachgezogen (`sudo install` + `systemctl restart
ai-village-webui.service`), analog zum bisherigen Vorgehen bei
`ai-village-auditor.service`/`ai-village-meeting-scheduler.service` –
danach lieferten alle drei Routen 200/JSON wie erwartet.

## Fix (`scripts/install-runtime.py`)

- Ziel-Konstruktion aus `main()` in eine eigenständige, importierbare
  Funktion `build_targets(source)` extrahiert – dieselbe Drift wäre
  bislang nur live sichtbar geworden (wie gerade eben bei P64), jetzt
  direkt unittestbar ohne systemd/Root/Dateisystem zu simulieren.
- `web/webui.py` und die drei `web/observatory.*`-Dateien zur Ziel-Liste
  hinzugefügt.
- **Ausführbarkeits-Sonderfall gefunden und behoben:** anders als jede
  andere `.py`-Datei in dieser Liste (die alle via `python3 <pfad>`
  aufgerufen werden) startet `ai-village-webui.service` seine Datei
  **direkt** (`ExecStart=/usr/local/lib/ai-village/webui.py`, live per
  `systemctl cat` bestätigt) – erfordert das Ausführbarkeitsbit. `put()`s
  gemeinsamer Standardmodus (`0o644`) hätte das stillschweigend entfernt
  und den Dienst beim nächsten Install lahmgelegt. Explizites
  `chmod(0o755)` nach dem generischen Kopier-Loop ergänzt.
- Automatischer Neustart von `ai-village-webui.service` nach jedem
  Install ergänzt – im Erfolgs- **und** im Rollback-Pfad, analog zum
  bereits bestehenden `ai-village-memory-gateway.service`-Muster.

## Tests (`tests/test_install_targets.py`, neu)

- Beide Zieldateien-Gruppen sind tatsächlich in `build_targets()`
  enthalten und zeigen auf die richtigen Quellpfade.
- Der `webui.py`-Zielpfad stimmt mit dem live per `systemctl cat`
  bestätigten `ExecStart`-Pfad überein.
- Alle Quelldateien aus `build_targets()` existieren tatsächlich im
  Checkout.
- **Generischer Abgleich gegen das Release-Manifest:** jede
  `web/*.py`- und `village/*.py`-Datei aus `RELEASE_FILES`, die nicht
  explizit als eigenständiger Dienst ausgenommen ist (`observer.py`,
  `telemetry-collector.py` – jeweils eigene Lebenszyklen), muss auch in
  `build_targets()` auftauchen. Verhindert genau diese Fundklasse für
  jede zukünftige Datei, nicht nur für die beiden hier gefundenen.

**Gegen den alten Code reproduziert:** `test_webui_and_observatory_assets_are_covered`
schlug vorher fehl (`KeyError`/fehlender Eintrag), ebenso der generische
Manifest-Abgleichstest (`missing=['web/webui.py', 'web/observatory.html', ...]`).

Gesamtsuite: 703 Tests, OK.

## Rollout

Nur `scripts/install-runtime.py` betroffen (reiner Deployment-Code, keine
Laufzeitänderung für Bewohner). Rollout über `install-runtime.py` selbst –
diesmal als echter End-to-End-Beweis, dass der Fix wirkt: ein normaler
Lauf sollte `webui.py`/`observatory.*` jetzt selbstständig aktualisieren
und `ai-village-webui.service` automatisch neu starten, ohne den bisher
nötigen manuellen Zwischenschritt.
