# P31 – Pflicht-Knowledgebase-Gate (explizite Betreiber-Intervention)

Date: 2026-09-27
Verification class: `LOCAL_VERIFIED` (Host-Rollout folgt)
Betreiberauftrag: „Zwinge dazu jeden Agent die Knowledgebase zu nutzen und relevantes
Wissen für die Gemeinschaft zu teilen.“

## Wichtig: das ist eine dokumentierte Forschungsintervention, kein stiller Default

Der ausgelieferte Standard (`config/runtime-policy.json`) bleibt unverändert
(`knowledgebase_gate: advisory`, identisch zum bisherigen Verhalten). Die Umstellung auf
`mandatory` erfolgt ausschließlich über eine lokale Host-Konfigurationsdatei
(`config/interventions/knowledgebase-mandatory.json` → `/etc/ai-village/runtime-policy.local.json`)
und wird hier als das dokumentiert, was sie ist: eine bewusste Änderung des
Forschungsdesigns auf ausdrücklichen Betreiberwunsch, kein automatisch gewordener neuer
Normalzustand.

## Umsetzung

- `village/policy.py`: neues Feld `AgentPolicy.knowledgebase_gate` (`advisory`|`mandatory`,
  ungültige Werte fallen sicher auf `advisory` zurück).
- `village/collaboration.py`: `CooperationCheckpoint` bekommt ein `hard`-Flag.
  `assess(..., require_shared_record=True)` verlangt für den `record`-Schritt zusätzlich
  `scope=shared` im zugehörigen `memory_result`-Event (nicht nur irgendeine Aufzeichnung)
  und markiert sowohl `orient` als auch `record` als `hard`.
- `web/runtime.py`:
  - `assess_collaboration(..., require_shared_record=(policy.knowledgebase_gate=='mandatory'))`.
  - `memory_result`-Events tragen jetzt das `scope`-Feld (`scope=private`/`scope=shared`),
    ohne das wäre die Unterscheidung nicht prüfbar.
  - `guard()`: Schwellenwert für Blockierung ist `1` statt `3` Versuchen, wenn
    `checkpoint.hard` gesetzt ist – **nur** für `orient`/`record`. Der `consult`-Schritt
    (Peer-Verfügbarkeit ist eine soziale, keine Wissens-Voraussetzung) behält seine
    bestehende Kulanz, um Deadlocks bei kleinen Modellen zu vermeiden.
- Prompt (voll und kompakt): `collaboration_checkpoint.enforcement` wird jetzt korrekt als
  `"immediate"` oder `"soft_until_three_misses"` beschrieben (vorher stand im vollen Prompt
  fälschlich immer „first two misses are nudges“, was unter `mandatory` nicht mehr stimmen
  würde). Zusätzlich ein expliziter Satz, dass eine private Aufzeichnung eine
  Teilen-Anforderung nicht erfüllt.

## Tests

`tests/test_reliability.py::MandatoryKnowledgebaseGateTests` (4 Tests, über echten
`Resident.snapshot()`-Zyklus, nicht nur synthetisch gesetzten Checkpoint):
1. Advisory-Default: unverändert 3 Versuche Kulanz.
2. Mandatory: blockiert bereits beim ersten Versuch ohne vorherige Suche.
3. Mandatory: eine private `memory_remember` erfüllt die Teilen-Pflicht nicht, eine mit
   `scope=shared` schon.
4. Ungültiger Policy-Wert fällt sicher auf `advisory` zurück.

Gesamtsuite: 393 Tests, OK.

## Risiko und Messplan

Laut Plan (`docs/analysis/MCP-GRAPHRAG-PLAN-2026-09-27.md`, Abschnitt 2) sollte dies
eigentlich A/B gemessen werden, bevor es zum Default wird. Das bleibt richtig für eine
spätere Standardänderung; für diesen expliziten Betreiberauftrag ist es als sofort
wirksame, aber jederzeit rückbaubare lokale Intervention umgesetzt (Datei entfernen +
Neustart = zurück zu `advisory`). Ein Messfenster nach dem Rollout zeigt, ob die
Mandatory-Regel Agents in Sackgassen zwingt (Anstieg von `collaboration_gate` ohne
nachfolgende Erfüllung) oder tatsächlich mehr geteiltes Wissen erzeugt
(`agents_with_memory_write`, Anteil `scope=shared` an `memory_remember`).

## Offen

Host-Rollout inklusive der Intervention-Datei; Messfenster danach.
