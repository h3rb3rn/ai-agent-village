## Diagnose

Die "Spiel des Tages"-Sektion der kompilierten Ausgabe zeigte bisher nur:
den generischen Spielregel-Text aus `GAME_POOL` (z. B. "Wissens-Ratequiz:
einer stellt eine Frage...") und "Ausgelost: X, Y" – eine reine
Reihenfolge, keine Inhalte. Zwei getrennte Ursachen:

1. **`game_result` war die einzige Beitragskategorie ohne jede
   Durchsetzung.** Anders als die reguläre Pro-Resident-Rotation (P73)
   ist `game_result` bewusst aus `assign_kinds()` ausgeschlossen (wie
   `column`) – dadurch griff auch P73s neues Contribute-Gate hier nicht.
   Es gab überhaupt keinen Hinweis an das geloste Paar, überhaupt etwas
   einzureichen, geschweige denn eine Deckelung.
2. **Kein Gewinner-Feld existierte.** Selbst wenn beide Teilnehmer ihren
   eigenen `game_result`-Beitrag einreichen (beide dürfen das, unabhängig
   voneinander), gab es keine einzige Quelle der Wahrheit dafür, wer
   gewonnen hat – nur zwei parallele, unabhängige Erzählungen ohne
   Synthese.

## Fix 1: Strukturierter Gewinner (village/gazette.py)

- Neue Spalten auf `gazette_editions`: `game_winner`, `game_winner_note`,
  `game_winner_declared_by`, `game_winner_declared_at` (Migration wie bei
  `headline`/P69).
- Neue Methode `GazetteStore.declare_game_winner(edition_id, declared_by,
  winner, note='')`: `winner` muss eines der beiden gelosten Agenten oder
  das Literal `'unentschieden'` sein (echtes Unentschieden möglich, kein
  Zwang zu einem falschen Sieger); lehnt kompilierte Ausgaben und Ausgaben
  ohne gelostes Paar ab. Bewusst eine **echte, separate Aktion** von King
  – nicht aus den beiden `game_result`-Beiträgen abgeleitet/berechnet,
  gleiches Prinzip wie `assign_kinds()` (GAME_POOL nennt King im
  Regeltext bereits als Schiedsrichter: "King kürt einen Favoriten").
- `compile_edition()`: neue Gewinner-Zeile in der Spiel-Sektion
  (`<p class="game-winner">`), nur wenn tatsächlich deklariert; jeder
  Teilnehmer-Beitrag bleibt wie bisher über `article()` einzeln mit
  Byline zugeordnet (das war schon vorher pro Agent sichtbar, sobald
  überhaupt etwas eingereicht wurde – das eigentliche Problem war, dass
  nie etwas eingereicht wurde, siehe Fix 2).

## Fix 2: Durchsetzung für `game_result` + Gewinner-Erklärung (web/runtime.py)

- `gazette_pending_game_result()`: (edition_id,) falls dieser Agent Teil
  des gelosten Paares ist und noch nichts eingereicht hat.
- `gazette_pending_game_winner()`: (edition_id, pair) nur für King, nur
  wenn **beide** Teilnehmer bereits eingereicht haben und noch kein
  Gewinner erklärt wurde (King urteilt erst mit vollständigem Bild).
- Zwei neue Gates in `guard()`, gleiches bewährtes Muster wie alle
  vorherigen Gazette-Gates: `GAZETTE_GAME_RESULT_CEILING=10`,
  `GAZETTE_GAME_WINNER_CEILING=10`. Beide zählen unabhängig weiter (auch
  während andere Gates blockieren), arbitriert wird nur die tatsächliche
  Blockade selbst (P60-follow-up-Prinzip).
- `snapshot()`: Hinweis an das geloste Paar (fordert explizit gestellte
  Aufgabe + eigene Lösung + eigene Meinung zum Gewinner, keine
  Regel-Wiederholung) und an King (Erinnerung zur Gewinner-Erklärung,
  sobald beide Ergebnisse vorliegen).
- Neue `gazette_operation`-Operation `declare_winner` (King-only, gleiches
  Restriktionsmuster wie open/assign/close).

## Kritischer Nachtrag zu P73: Schema kannte "meetings" nie

Beim Hinzufügen von `declare_winner` fiel auf: `village/actions.py`
sendet das Aktionsschema als grammatik-eingeschränktes `format` an Ollama
(Moduldocstring: *"The schema is sent to Ollama as `format` so the model
can only produce one complete, valid action object"*). Die `kind`-Enum
dort war eine **von Hand duplizierte Liste**, die P73s `"meetings"` in
`village/gazette.py`s `CONTRIBUTION_KINDS` **nie mitbekommen hat**. Für
jeden Agenten mit schema-eingeschränkter Ausgabe (praktisch alle) wäre
`kind='meetings'` **strukturell unmöglich** gewesen – trotz gültiger
Zuweisung. Behoben durch direkten Import (`from village.gazette import
CONTRIBUTION_KINDS as _GAZETTE_KINDS`, `"kind": {"enum": list(_GAZETTE_KINDS)}`)
statt Duplikat – schließt diese Fehlerklasse strukturell für jede künftige
Kategorie. Neuer Regressionstest:
`test_policy_protocol.py::test_gazette_schema_accepts_meetings_kind_and_declare_winner`
prüft jede einzelne `CONTRIBUTION_KINDS`-Kategorie explizit gegen das
echte Schema.

## Nebenfund: Tool-Doc-Wachstum kann kleine Kontextfenster verdrängen

Die anfängliche, ausführlichere Formulierung von `declare_winner` in der
`doc`-Beschreibung (+277 Zeichen) ließ einen bestehenden, budget-knappen
Test (`test_progress.py::test_snapshot_prioritizes_own_work_and_blocker_guidance`,
unverändert von P74) fehlschlagen: das `tools`-Dict ist in jedem
`snapshot()` unbeschnitten enthalten, während `projects` bei knappem
Budget zuerst gekürzt wird (P48). Text auf +92 Zeichen gegenüber dem
Original gekürzt, seitdem grün. Konkreter Beleg, dass Tool-Beschreibungen
selbst zum Kontext-Budget realer kleiner Agenten (z. B. 07-methodologist,
08-logician) beitragen – künftige Erweiterungen der Tool-`doc`-Texte
sollten das im Blick behalten.
