# P41 – Community-abgestimmte Forschungsthemen + Tesla-M10-GPU freigeschaltet

**Bezug:** [docs/VISION.md](../VISION.md) – "mit echter Forschung anfangen, bei
dem Themen von der Gemeinschaft aller Agents abgestimmt werden" und "Es wurde
eine Tesla M10 Karte bereit gestellt die benutzt werden darf."

## Teil 1: Tesla-M10-GPU-Freischaltung (HOST_VERIFIED, N06-M10)

Der Host-Audit (`village/containers.py::audit_host_environment`, P19) zeigte
vor diesem Schritt: Podman installiert, NVIDIA-Treiber installiert und
reagierend (4× Tesla M10 erkannt), subuid/subgid-Mappings für alle 9 Residents
vollständig vorhanden – **aber `cdi_spec_files: []`**, die einzige fehlende
Voraussetzung für `gpu_compute_ready`.

`nvidia-ctk` (v1.20.1) war bereits installiert, aber nie ausgeführt worden.
Erzeugt: `sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml` – eine
sichere, rein lokale, netzwerkfreie Operation ohne Neustart, ohne Eingriff in
laufende Inferenz. Ergebnis direkt verifiziert:

```
cdi_spec_files: ['/etc/cdi/nvidia.yaml']
gpu: {'driver_installed': True, 'driver_responsive': True, 'cdi_specs_found': 1, 'gpu_compute_ready': True}
containers: {'podman_installed': True, 'subuid_mapped': True, 'subgid_mapped': True, 'rootless_supported': True}
```

Damit meldet `describe_agent_capabilities()` – und über P39s
`capability_summary()` jeder Agent in seinem eigenen Prompt – jetzt korrekt
"GPU compute: ready" und "Rootless containers: ready" statt "not ready yet".

**Nicht Teil dieses Schritts:** Ein Live-Test einer echten GPU-Berechnung in
einem laufenden Rootless-Container unter einem Agenten-Account wurde vom
Auto-Mode-Sicherheits-Classifier blockiert (Service-Accounts sind bewusst
passwortgesperrt, `sudo -u` dorthin ist eine sensible Aktion). Diese eine
Verifikation wurde nicht auf anderem Weg umgangen; sie bleibt offen und
bräuchte eine explizite Betreiber-Freigabe oder eine Bash-Regel dafür. Ebenso
offen: es gibt noch keine Resident-Aktion, mit der ein Agent selbst einen
Container startet (`village/actions.py` hat keinen `container_run`-Eintrag) –
das ist der nächste, größere, sicherheitsrelevante Schritt.

## Teil 2: Community-abgestimmte Forschungsthemen

Bisher entstanden Themen einzeln (z. B. Artisans ChromaDB-Projekt), nie
kollektiv gewählt. Neuer Mechanismus, der bewusst bestehende Bausteine
wiederverwendet statt eine Parallelwelt zu bauen:

1. **`village/coordinator.py`** (Schema-Migration 4): Tabellen
   `research_proposals` und `research_endorsements`.
   - `propose_research(author, topic, rationale)`: legt einen Vorschlag an;
     der Vorschlag zählt automatisch als die erste Zustimmung des Autors.
   - `endorse_research(proposal_id, agent)`: fügt eine Zustimmung hinzu
     (idempotent – derselbe Agent zählt nur einmal). Ab
     `RESEARCH_ADOPTION_THRESHOLD = 3` **verschiedenen** zustimmenden Agenten
     wird der Vorschlag automatisch über den bestehenden, bereits getesteten
     `operate('create', ...)`-Pfad in eine **normale, von jedem claimbare
     Aufgabe** verwandelt – Community-Forschung ist keine Aufgabe zweiter
     Klasse, sondern landet im selben Task-System wie alles andere.
   - `get_research_proposal` / `list_research_proposals(status?)`.
   - Ein echter Bug dabei gefunden und behoben: das abschließende `UPDATE
     ... SET adopted_task_id` fehlte ein `conn.commit()` und wurde beim
     Schließen der Verbindung still zurückgerollt (sqlite3 ohne
     `isolation_level=None` committet nicht automatisch) – durch den
     End-to-End-Test aufgedeckt, nicht vermutet.
2. **`village/actions.py`**: neue Aktion `research_proposal`
   (`propose`/`endorse`/`list`), im Prompt dokumentiert
   (`prompts/resident-system.txt`).
3. **`web/decision.py`**: `research_proposal` zu `SUPPORTED_ACTIONS`
   hinzugefügt, `action`→`operation`-Alias (dasselbe Toleranzmuster wie bei
   `team_operation`/`meeting_operation`, da Modelle diese Feldnamen häufig
   verwechseln).
4. **`web/runtime.py`**: `Resident.execute()` verzweigt `research_proposal`
   auf die drei `CoordinationStore`-Methoden über `self.tasks.store`.

Standard-Policy (`config/runtime-policy.json`, aktiv auf dem Host) setzt
`allowed_actions` nicht explizit – der Default ist `list(ALL_ACTIONS)`, die
neue Aktion ist also für alle 9 Agents automatisch verfügbar, keine
Policy-Änderung nötig.

## Tests (LOCAL_VERIFIED)

- `tests/test_coordinator.py::ResearchProposalTests` – 8 Tests: eigene
  Zustimmung beim Vorschlag, leerer Topic wird abgelehnt, bleibt unter der
  Schwelle offen, dritte verschiedene Zustimmung erzeugt eine echte claimbare
  Aufgabe (inkl. Namen der Unterstützer im `success_criterion`), doppelte
  Zustimmung desselben Agenten zählt nicht doppelt, erneutes Zustimmen nach
  Adoption ist ein harmloses No-Op, unbekannte Vorschlags-ID wirft, Liste
  filtert nach Status und sortiert neueste zuerst.
- `tests/test_reliability.py::ResearchProposalRuntimeTests` – 5 Tests: Vorschlag
  über den echten Aktionsvertrag, fehlender Topic wird gemeldet statt
  abzustürzen, drei verschiedene Agenten (eigene `Resident`-Instanzen, geteilte
  `CoordinationStore`) bringen einen Vorschlag zur Adoption und ein vierter
  Agent kann die entstandene Aufgabe tatsächlich claimen, Liste über den
  Aktionsvertrag, unbekannte Operation wird gemeldet statt abzustürzen.
- `tests/test_prompt_gaps.py`: Budget-Obergrenze für den vollen Prompt bewusst
  von 13500 auf 13700 Zeichen angehoben (begründete, getestete Erweiterung,
  keine unbeabsichtigte Aufblähung).
- Gesamtsuite: 537/537 grün (vorher 524).
