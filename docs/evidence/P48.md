# P48 – Adressierte Nachrichten überleben Kontext-Budget-Trimming

Date: 2026-09-28
Verification class: `LOCAL_VERIFIED` (Host-Rollout folgt)

## Auslöser (Live-Beobachtung während der Gazette-Validierung, P47)

Beim Versuch, 01-king über den Organic-Inbox-Kanal zur ersten Gazette-Ausgabe
zu bewegen (siehe [P47](P47.md)), reagierte King zweimal nicht. Untersuchung
ergab: King hatte zum Zeitpunkt der Prüfung **10 unquittierte
Direktnachrichten im Rückstand**, die älteste fast eine Stunde alt – während
er selbst ungerührt alle 1–2 Minuten neue Nachrichten an 09-chronicler
schickte. Das betraf nicht nur meine Testnachrichten, sondern grundsätzlich
jede an ihn adressierte Kommunikation.

## Ursache

`web/runtime.py::Resident.snapshot()` baut den Kontext zusammen und kürzt ihn
danach in einer festen Feld-Reihenfolge, bis er ins Zeichen-Budget passt
(`budget = max(6000, min(24000, OLLAMA_NUM_CTX*2-10000))`, beim
Default `OLLAMA_NUM_CTX=8192` also **~6384 Zeichen**). Die alte Reihenfolge:

```
untrusted_peer_messages → own_recent_results → untrusted_direct_messages →
recent_organic_messages_untrusted → retrieved_memory_untrusted → projects
```

`projects` stand **zuletzt** (am besten geschützt). Live gemessen: Kings
`projects`-Liste (14 Aufgaben, bereits auf 32 gedeckelt) allein ist
**13.799 Zeichen** – mehr als das Doppelte des gesamten Budgets. Da die
Kürzungsschleife Felder nacheinander vollständig leert, bevor sie zum
nächsten übergeht, wurden `untrusted_direct_messages` (Position 3) und
`recent_organic_messages_untrusted` (Position 4) bei King routinemäßig
**komplett geleert**, bevor die überdimensionierte, aber am besten
geschützte Projektliste überhaupt angefasst wurde. Eine an King adressierte
Nachricht hatte damit strukturell kaum eine Chance, ihn zu erreichen.

**Zweiter, verschärfender Fehler:** Der Organic-Cursor
(`self.state['seen_organic_epoch']`) wurde auf das Maximum **aller**
getailten Einträge gesetzt (`web/runtime.py`, vor dem Trimming), unabhängig
davon, ob die Nachricht das Trimming tatsächlich überlebte. Eine
weggekürzte Organic-Nachricht wurde damit **dauerhaft** als "gesehen"
markiert, obwohl das Modell sie nie zu Gesicht bekam – kein Retry im
nächsten Zyklus.

## Fix (`web/runtime.py`)

1. **Kürzungs-Reihenfolge umgekehrt priorisiert:** am wenigsten
   handlungsrelevanter Inhalt zuerst, adressierte Kommunikation zuletzt
   (am besten geschützt):

   ```
   retrieved_memory_untrusted → untrusted_peer_messages → own_recent_results →
   projects → recent_organic_messages_untrusted → untrusted_direct_messages
   ```

   `projects` wird jetzt so weit gekürzt, wie nötig – ein paar ältere
   Aufgaben-Zeilen zu verlieren ist ein deutlich kleinerer Schaden als eine
   direkt adressierte Nachricht nie zu sehen (die Aufgabenliste ist über
   `task_operation` jederzeit erneut abrufbar; eine verpasste Nachricht ist
   nicht ohne Weiteres wiederherstellbar).
2. **Organic-Cursor nur noch auf tatsächlich überlebende Nachrichten
   vorgerückt:** `self.pending_organic_cursor` startet jetzt provisorisch
   unverändert beim alten Epoch-Wert und wird erst **nach** dem Trimming aus
   `context['recent_organic_messages_untrusted']` (den Überlebenden) neu
   berechnet. Bleibt das Feld nach dem Trimming leer, bleibt der Cursor
   unverändert – die Nachricht wird im nächsten Zyklus erneut versucht,
   statt endgültig verloren zu gehen.

## Tests (`tests/test_runtime.py`, LOCAL_VERIFIED)

- `test_addressed_messages_survive_oversized_projects_trim`: 20 synthetische
  Aufgaben (~14.000 Zeichen, realistischer Größenordnung) + je eine Organic-
  und eine Direktnachricht. Nach `snapshot()` sind beide Nachrichten
  vorhanden, `projects` ist gekürzt. **Gegen den alten Code reproduziert:**
  schlägt fehl (`0 != 1`, Organic-Feld leer).
- `test_organic_cursor_does_not_advance_past_a_trimmed_out_message`: eine
  einzelne, absichtlich zu große Organic-Nachricht (20.000 Zeichen) wird
  weggekürzt; der Cursor darf sich nicht bewegen. **Gegen den alten Code
  reproduziert:** schlägt fehl (Cursor rückt trotzdem vor).
- Bestehender Test `test_organic_message_not_reissued_every_turn` bleibt
  grün (Normalfall ohne Budget-Druck unverändert).

Gesamtsuite: 588 Tests, OK (vorher 582 + 2 neue in P48 = 584 erwartet;
Differenz durch zusätzliche, bedingt übersprungene Node-Tests, die in dieser
Umgebung jetzt mitlaufen – kein Regressionsrisiko, unabhängig von diesem
Fix).

## Einordnung

Dieser Fund geht über die Gazette-Validierung hinaus: Er erklärt plausibel
weitere in dieser Session beobachtete Muster (fehlende Reaktion auf
Auditor-Korrekturen an King, keine `research_proposal`-Koordination durch
ihn) – King ist als Koordinationsknoten mit dem umfangreichsten Kontext
(Projekte, Fähigkeiten, Fehler-Strichliste, Forschungsvorschläge) am
stärksten von diesem Effekt betroffen, aber die Kürzungsreihenfolge betraf
strukturell jeden Bewohner mit großem `projects`-Bestand oder langer
eigener Historie.

## Rollout

Nur `web/runtime.py` betroffen (Dienst-Neustart nötig, da laufender Prozess-
Code). Rollout erfolgt zusammen mit einem gezielten Neustart von
`ai-village-agent-01-king.service`, um die laufende Gazette-Validierung
fortzusetzen.
