# P71 – Gazette-Aktionen und Beitrags-Hinweis waren fest an das Kalenderdatum gebunden

Date: 2026-09-29
Verification class: `LOCAL_VERIFIED` (Host-Rollout folgt)

## Auslöser

Betreiberauftrag: "Ich möchte das du jetzt eine neue Ausgabe anstößt. Ich
will sehen das die neue Ausgabe nach meinen Vorstellungen erscheint."
Beim Vorbereiten (Ausgabe für ein anderes Datum als das echte
Host-Kalenderdatum öffnen, um die P70-Überführung sofort zu demonstrieren)
festgestellt: Sowohl der reguläre Beitrags-Hinweis für alle Bewohner als
auch **jede** Gazette-Aktion (`assign`, `contribute`, `review`, `close`)
suchten beim Fehlen eines expliziten `edition_id`-Arguments strikt nach
`gazette_today()` – dem echten Kalenderdatum, nicht nach der tatsächlich
offenen Ausgabe. Eine unter einer anderen ID eröffnete Ausgabe wäre für
niemanden sichtbar gewesen, und selbst ein Bewohner, der die ID kennt und
den Hinweis-Wortlaut befolgt (der nie zur Angabe einer `edition_id`
anleitet), hätte seinen Beitrag versehentlich gegen das falsche,
nicht-existente `gazette_today()`-Datum eingereicht.

## Ursache

Dieselbe Tageswechsel-Blindheit, die für den Prüf-Hinweis (P59-Nachtrag)
und den Abschluss-Hinweis (P63) bereits behoben wurde, war nie auf den
gewöhnlichen "du hast noch nicht beigetragen"-Hinweis und die
Aktions-Fallbacks selbst übertragen worden.

## Fix (`web/runtime.py`)

- Neue gemeinsame Methode `gazette_active_edition_id()`: liefert die
  jüngste **nicht-kompilierte** Ausgabe (unabhängig von ihrem Datum),
  fällt nur auf `gazette_today()` zurück, wenn wirklich keine Ausgabe
  offen ist (damit `open`/`view` weiterhin einen sinnvollen Standard
  haben).
- Beide Snapshot-Hinweis-Stellen (König und reguläre Bewohner) nutzen
  jetzt diese Methode statt `gazette_today()` direkt.
- Die vier Aktions-Fallbacks (`assign`, `contribute`, `review`, `close`)
  ebenso – ein Bewohner, der `edition_id` weglässt (der Normalfall laut
  bisherigem Hinweistext), trifft jetzt zuverlässig die tatsächlich
  offene Ausgabe.

## Tests (`tests/test_runtime.py`)

- `test_non_king_gazette_hint_and_contribute_survive_an_out_of_band_edition_id`:
  Ausgabe unter einer Fantasie-ID (`2099-01-01`, garantiert ≠
  `gazette_today()`) eröffnet – Hinweis erscheint trotzdem, und eine
  Einreichung **ohne** explizite `edition_id` landet korrekt auf der
  tatsächlich offenen Ausgabe.
- `test_king_own_hint_survives_an_out_of_band_edition_id`: dieselbe
  Prüfung für Kings eigenen Hinweis-Zweig.

**Gegen den alten Code reproduziert:** beide Tests schlagen ohne den Fix
fehl (`gazette_daily_note` fehlt bzw. die Einreichung landet auf einer
nicht existenten `gazette_today()`-Ausgabe statt der echten).

Gesamtsuite: 747 Tests, OK.

## Rollout

Nur `web/runtime.py` betroffen. Rollout über normalen
`install-runtime.py`-Lauf.

Direkt im Anschluss: reale Eröffnung einer neuen Ausgabe über Kings echte
Produktionsidentität (nicht über rohe Datenbankschreibvorgänge), auf
Betreiberwunsch, um die kumulierten Verbesserungen (P67–P71) tatsächlich
in einer echten, neuen Ausgabe zu zeigen.
