# P50 – `install-runtime.py --no-start` stoppte entgegen eigener Beschreibung laufende Dienste

Date: 2026-09-28
Verification class: `LOCAL_VERIFIED` (Host-Fix bereits operativ angewendet)

## Auslöser (Live-Beobachtung während der Gazette-Validierung, P47–P49)

Nach dem zweiten `--no-start`-Rollout für P49 waren **8 von 9 Bewohnern
inaktiv** – `systemctl is-active` lieferte `inactive`, kein Absturz, sauberer
Exit (`status=0/SUCCESS`), Journal zeigte explizit `Stopping ... Deactivated
successfully ... Stopped` für jeden betroffenen Dienst, exakt zum Zeitstempel
des `--no-start`-Installs (`runtime-20260928T150233...`). Nur King lief noch,
weil er nach jedem Install gezielt manuell neu gestartet wurde – alle
anderen blieben unbemerkt tot.

## Ursache (`scripts/install-runtime.py`)

Die Hilfetext-Beschreibung von `--no-start` versprach: *"Install files
without starting or restarting resident services"* – impliziert: laufende
Dienste bleiben unberührt. Tatsächlich stoppte der Installer **vor** dem
Kopieren der Dateien unbedingt alle aktuell aktiven Bewohner-Units:

```python
if not args.provision_only and active:
    subprocess.run(['systemctl','stop',*active],check=True)
```

`--no-start` griff nur **danach**, beim (unterdrückten) Wiederstart. Der
ursprüngliche Zweck des unbedingten Stopps ist plausibel: eine laufende
Python-Instanz hält ihr altes Modul im Speicher, ein reiner Dateitausch
würde ohne Neustart ohnehin nichts bewirken – für den **normalen**
Rollout-Pfad (Dienste danach automatisch neu gestartet) korrekt. Für einen
gezielten `--no-start`-Rollout in eine **aktiv laufende** Dorfsimulation
(dieser Session-Anwendungsfall: einen einzelnen Agenten kontrolliert
validieren, ohne die anderen anzufassen) war das aber falsch – und im
ursprünglichen Anwendungsfall (Install während bewusster Pause) wäre
`active` ohnehin leer gewesen, der Bug also dort nie sichtbar geworden.

## Fix

Neue, direkt testbare Funktion `should_stop_active_services(active,
provision_only, no_start)`: Stoppen nur noch, wenn tatsächlich etwas aktiv
ist, kein reiner Provisionierungslauf **und** `--no-start` nicht gesetzt
ist. Hilfetext und Erfolgsmeldung präzisiert, damit sie das tatsächliche
Verhalten beschreiben:

> "Install files without stopping, starting or restarting currently running
> resident services; they keep running the old code until separately/
> manually restarted"

## Tests (`tests/test_install_no_start.py`, LOCAL_VERIFIED)

4 Tests: `--no-start` stoppt nichts trotz aktiver Dienste (der eigentliche
Bug); ein normaler Install stoppt weiterhin aktive Dienste (nötig, um den
Codetausch überhaupt wirksam zu machen); nichts zu stoppen, wenn nichts
aktiv ist; `--provision-only` stoppt nie etwas. **Gegen den alten Code
reproduziert:** `AttributeError` (Funktion existierte nicht, alte Logik war
inline und ignorierte `no_start` für die Stopp-Entscheidung vollständig).

Gesamtsuite: 598 Tests, OK.

## Sofortmaßnahme (bereits durchgeführt)

Alle 8 betroffenen Bewohner-Dienste wurden manuell neu gestartet
(`systemctl start` je Unit), bevor der Code-Fix überhaupt geschrieben war,
um die laufende Gazette-Validierung fortsetzen zu können. Der Code-Fix
selbst verhindert eine Wiederholung bei künftigen `--no-start`-Rollouts.

## Rollout

Nur `scripts/install-runtime.py` betroffen – reines Kontrollskript, kein
laufender Agenten-Code, kein Dienst-Neustart für die Wirksamkeit nötig
(wirkt beim nächsten Aufruf des Skripts selbst).
